# KAN-203 execution history implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task.

**Goal:** Reopen retained execution attempts and inspect safe traces, precise invalidation and recovery state.
**Architecture:** Extend KAN-202's immutable manifests, shared PostgreSQL persistence and leased worker. Compute freshness from exact source/configuration/dependency identities without rewriting historical outcomes. Store evaluations independently from generation; KAN-204 owns evaluator orchestration.
**Tech Stack:** TypeScript, Next.js 16, PostgreSQL/Drizzle, Vitest, Playwright.
**Spec:** Jira KAN-203 acceptance criteria (fetched 2026-10-30); approved KAN-199 design; docs/development/execution-contract.md.

## Global Constraints

- Do not improve/rebuild extraction, matching or splitting algorithms, conduct paid experiments, choose winning models or change customer/shared settings.
- Use existing Vitest and Playwright conventions with isolated test persistence and no paid model calls.
- Keep references out of generation inputs; reference/evaluator/profile changes affect evaluations independently.
- Retain immutable outcomes; successful publication is atomic; latest failed attempts cannot fall back to older success.
- Preserve owner authorization, credential redaction, worker claims and no automatic resend of uncertain paid calls.
- Branch from KAN-200; publish to origin and github; PR targets KAN-200 and remains open.

## Review Focus

- An older browser has stale prerequisite IDs: reject without creating work.
- Draft changes while queued/running: frozen work retains its inputs and becomes outdated appropriately.
- Concurrent/expired worker claims: old workers cannot publish or settle after loss of ownership.
- A credential appears in provider response/log text: persisted history and owner trace reads redact it.
- More than fifty executions: old history remains accessible with deterministic pagination.

### Task 1: Durable history, lineage, safe traces and independent evaluation associations

**Ownership:** src/modules/development backend files, execution API routes, tests/kan-203-history.test.ts, docs/development history contract. No UI edits.
**Interfaces:** Extend existing Execution/SectionAttempt/ExecutionManifest compatibly. Provide documented typed history/freshness and evaluation association exports for Task 2. Keep raw internal worker requests usable for replay while owner-facing history is redacted.

- [ ] Add behavior-first API/integration tests using isolated PostgreSQL and stubbed completions: retained reruns, failed latest prerequisite rejection, transitive invalidation, source/config/mode changes, evaluator/reference independence, draft edits during execution, stale-tab rejection, concurrent sends/publications, safe queued recovery and uncertain-send interruption.
- [ ] Extend manifests with reference identities outside generation identity; persist section/call start/end times, latency, role/requested/actual route identity, usage/cost/trace associations and safe intermediate replies/logs. Reuse existing call receipts; sanitize before persistence where safe, preserve replay integrity, and redact all owner-facing reads. Guard trace access with owner authorization and experiment association.
- [ ] Add durable independent evaluation associations with exact attempt/output/profile/evaluator/reference identity and separate statuses (unscored, failed, blocked, outdated, not_applicable plus lifecycle states). Provide safe association/read/freshness helpers only: no scoring orchestration, criteria editor or paid calls.
- [ ] Derive downstream freshness against current source snapshots, supplied current config, latest attempt IDs and transitive bindings. Reject stale prerequisites server-side. Support deterministic paginated retained history, retaining compatible existing responses.
- [ ] Audit claim operations for atomic ownership checks and recovery; prevent expired workers overwriting attempts or releasing another worker's claim. Preserve independently completed sections on another failure and explicit recorded retry policy. Document deployment capability limitations already present in KAN-202.
- [ ] Run focused Vitest including KAN-201/202 regressions, TypeScript and touched-file lint. Record red/green commands, results, exports and material limitations in task report. Leave changes uncommitted for controller commit/review packaging.
