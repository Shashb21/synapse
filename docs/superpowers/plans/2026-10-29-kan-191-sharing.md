> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Record the approved customer boundary and verify an executable reference policy before enforcement.
**Architecture:** An accepted ADR owns the decision and phased migration contract. A pure specification in specs/policies models allowed/denied decisions without production imports or I/O.
**Tech Stack:** TypeScript, Vitest, Markdown.
**Spec:** docs/superpowers/specs/2026-10-29-kan-191-sharing-design.md

## Global Constraints

- No runtime enforcement, migrations, UI or current access changes in KAN-191.
- Customer access requires verified identity, active seat, membership and same durable customer or explicit recorded admin exception.
- Only same-customer workspace owners with access may invite active same-customer seat holders; exceptions never delegate invitations.
- Platform admin access remains separate from customer-app access.
- Explicit legacy/default/demo/platform handling; no silent lockout or data deletion.
- Preserve unrelated edits. Parent owns commits, pushes, PR and Jira writes.

## Review Focus

- Stale memberships and changed seats: old customer access denied in intended policy.
- Admin status or password/demo provider alone: no app bypass.
- Missing ownership: no automatic classification or permission.
- External grant: exact principal/workspace binding, recorded approval, revocation and active seat retained.
- Denied invitation: member or external owner cannot onward-share.
