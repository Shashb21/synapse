# KAN-188 Run Payload Retention Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox syntax for tracking.

**Goal:** Keep uploaded document bytes available to parsing while excluding them from persisted Accuracy run records and run-list responses.
**Architecture:** The recorder owns safe telemetry input: derive bounded parse metadata before recording, and sanitize input-bearing steps before truncation. The run-list data layer projects historic input/steps safely. Document a deliberate operator cleanup rather than silently rewriting historical data at startup.
**Tech Stack:** TypeScript, Next.js, Drizzle/PostgreSQL, Vitest.
**Spec:** https://synapse21.atlassian.net/browse/KAN-188 (fetched 2026-10-29).

## Global Constraints

- Parsing continues to receive required document bytes.
- Persisted run inputs and run-list responses contain no content_base64/raw document payload.
- A large-upload regression test verifies response size is independent of document payload size.
- Historic payload cleanup/retention is documented and access controls remain enforced.
- Use this TypeScript repository's Vitest/database tests and browser tests where relevant.
- Preserve parsed text, model traces and unrelated module behavior; scope is raw uploaded bytes, not broad monitoring redaction (KAN-179).
- Do not modify the primary checkout's existing edits. Workers never push or open PRs; controller owns publishing to both remotes.

## Review Focus

- Small payloads and >40,000-character payloads: no full bytes or truncated base64 previews.
- Invalid parse inputs: initial error runs still record safe input.
- Historic parse steps already truncated by old trim(): discard their unsafe preview.
- Non-parse runs: ordinary JSON inputs and notes retain behavior.
- Unauthorized callers: owner gate denies before reads, including historic runs.

### Task 1: Prevent raw document retention and protect historic run reads

**Files:** Modify `src/accuracy/kernel/observability.ts` and optionally `src/accuracy/kernel/run.ts`; create a focused helper under `src/accuracy/kernel/` if needed. Add regression tests under `tests/`; extend `tests/accuracy-source-upload.test.ts` for real upload/DB proof. Add `docs/operations/accuracy-run-retention.md` for historic cleanup. Avoid unrelated API/UI changes.

**Interfaces:** Preserve `runAccuracyModule` processing input and existing recorder/list public signatures. A private or small exported sanitizer may implement metadata projection; enforce at recorder ownership so upload and seed-from-gold callers are both covered. Parse metadata includes source/workspace IDs, filename, MIME, checksum and decoded byte count where available; do not trust arbitrary extra input keys as safe. Derive missing checksum/byte count without modifying input. Use the same projection for accepted-input notes. Sanitize all new recorder structured telemetry against content_base64 keys before trim can create previews. For historic parse input/accepted-input steps, use safe metadata or remove unsafe truncated preview; sanitize historic structured payload keys throughout returned records. Prefer SQL-side projection for historic large input to avoid transferring full base64 from PostgreSQL; retain correctness and type clarity.
