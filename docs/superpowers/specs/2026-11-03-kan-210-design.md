# KAN-210: Development evaluation ownership

Binding requirements: Jira KAN-210. Retain useful Accuracy model-selection tools under Development; reuse existing real-customer-stage execution, evaluation, comparison and cost controls. Preserve authorization, reference separation, immutable histories, AI-off controls and unchanged effective live settings. Preserve benchmark commands, private files, JSON/CSV contracts, human review, reference resolution, historical prompts and saved-run identities. Do not migrate records or select/deploy a model.

Move the isolated historical benchmark and reference loaders to src/modules/development/evaluation/. Retain exactly the historical prompt/audit implementations within that ownership, free of Accuracy imports. Existing Accuracy callers may use compatibility re-exports of the moved reference tools. The benchmark is historical evidence, never validation of today's customer pipeline. Current-pipeline experiments continue through existing Development stages. A Development evaluation tools surface should explain this distinction and make retained reference/benchmark tools discoverable without adding paid dispatch or reading arbitrary private files.

Alternatives: replacing historical benchmark stages with current customer stages invalidates identities and historical comparisons; rebuilding a second experiment application duplicates current Development capabilities. Neither fits the ticket. The ownership move with compatibility evidence is the smallest coherent change.

Before changing paths, record a synthetic completed saved-run fixture and fixed prompt/audit/scoring identities against the original implementation. Assert these exact fixtures after the move, including no-provider review/resume. Never refresh an expected identity merely because relocation changed it; investigate and stop any incompatible move. Private customer artifacts must not enter git.
