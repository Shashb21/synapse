This inventory records the Task 1/Task 2 source review and the bounded final correction wave on 2026-10-29. It includes ordinary customer pages, account/workspace journeys, shared controls, the platform owner tools, historical run views, and every Accuracy Lab component. **Source review is not runtime proof.** Test evidence is identified separately below; Task 3 browser evidence is recorded in `kan-197-results.md`: all nine new acceptance cases passed initially; two wider-batch stage API fallback failures were corrected in the final wave. The final browser batch is recorded separately by Task 3, not assumed green here.

## Message and outcome ownership

- `src/modules/kernel/stage-errors.ts`: `TrustedApplicationError` preserves fixed application-owned correction text; provider errors use known provider categories. Unknown exception text and historical exception strings are never displayed. Customer recovery names business tasks (reading sources, extraction, mapping, prioritization, ideas and timeline). Owner copy adds provider-account/billing/connection remedies without raw payloads.
- `src/modules/auth/api-guard.ts`, `src/app/api/workspaces/_shared.ts`, `src/app/api/accuracy/_lib/request.ts`: keep expired sign-in, forbidden access, confirmed missing entities, malformed requests, size limits, workspace mismatch and known correction messages distinct. Schema field errors stay associated with the fields that need correction.
- `src/lib/post-json.ts`, `src/components/workspaces/model.ts`, `src/components/accuracy/claim-api.ts`, `src/components/room/room-channel.ts`: failed requests have confirmed/rejected/unknown outcomes. Unreadable, null, array, empty-object or lost replies do not establish successful writes. Browser-generated exceptions never supply public wording. Endpoint-specific consumers validate meaningful success fields where needed.
- A lost response means a write **may already have happened**. Copy asks the person to inspect current state before another mutation. Destructive source clear, workspace reset, shared ActionDialog, workspace membership/settings and consequential multi-step editors disable blind repetition and supply a read/check action. Local validation happens before submitting and keeps correction immediately available.
- Known server errors generally remain outcome-unknown unless their owner explicitly proves pre-write rejection. This is conservative: some server-only validation responses in ActionDialog preserve the draft but require checking/reloading current state before submission is re-enabled. HTTP 400 alone is not proof that earlier writes did not happen. This usability limitation needs final review; no blanket rejected classification was added.
- Checkpointed ingestion is the intentional exception: it can safely continue from recorded progress. Completed upload/parsing/extraction stages and saved axes/schedule changes remain real even if a later step fails. The UI names completed and unconfirmed steps separately.

Unexpected page-data failures fall through to `src/app/error.tsx`: “This page could not be loaded” plus “Try loading again” and “Choose a workspace.” The installed Next 16.3 guide documents the working `retry` prop; this is a read-only retry. Failed session/configuration reads no longer fabricate signed-out, AI-off or empty-data states. The boundary covers page/child rendering; it does not catch errors in its own root layout, as documented by Next.
