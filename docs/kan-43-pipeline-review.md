## One source-backed gap through the test contracts

`tests/accuracy-assembly-approval-integration.test.ts` has a concrete **synthetic** fixture: `fixture()` inserts `source.txt` and a parse block with text “Shared source text supports the selected item.” `gap()` builds “Approved exact gap” with a quote of “supports the selected item.” `publishAssembly()` inserts successful test extraction runs, publishes generated item versions, creates an applied extraction batch, records a `coverage_decide` run bound to the exact gap/tactic versions, and creates an assembly with those selections and reasons. Its test **“blocks managed live readers until approval and then serves exact approved payloads”** first observes `approval_required`, then calls `approve()`, reads the exact approved gap from `listDownstreamClaims`, checks the approved coverage pair, and executes a successful `merge_dedupe` downstream run. This is an actual executable integration-test path using real Postgres, but its input and module behavior are controlled fixtures, not a customer extraction or paid provider response.

The separate `tests/accuracy-assembly-feedback-store.test.ts` test **“records exact consumed items and immutable evidence for whole and subset feedback”** verifies feedback proof on a synthetic successful production consumer binding. It does not extend the same fixture run above; no single inspected test proves every step from a generated V0 through human approval, downstream consumption and feedback in one observed run. The contracts connect through persisted run IDs, item-version IDs, assembly fingerprint, review ID and consumer bindings. Source paths: `store/item-history-store.ts` (`publishGeneratedItemHistory`), `kernel/assembly-generation.ts` (`generateExtractionAssembly`), `domain/assembly.ts` (`checkAssembly`, `assemblyFingerprint`), `store/assembly-review-store.ts` (`reviewAssembly`, `approvedLiveInventory`), `kernel/run.ts` (`runAccuracyModule`), and `store/assembly-feedback-store.ts` (`listAssemblyFeedbackRuns`, `createAssemblyFeedback`).

## Deviations and rulings

- The original KAN-30 V1-versus-V3 example was illustrative. `runShallowAgenticCycle` records versions but its judge event says “Current latest-version policy”; it cannot itself choose an earlier supported V1. That remains an implementation/design gap.
- Deterministic source quote and assembly checks are useful safety gates, not semantic or clinical correctness. An approved assembly is eligible for managed downstream use, not proven complete or accurate.
- Production signals and KAN-42 contributor feedback are not gold outcomes. Only the isolated curated evaluator provides the supported source-item exact metrics. KAN-40's downstream dimensions are explicitly unscored.
- KAN-40's no-edit automatic gate in private benchmark copies is an experiment policy. It is not a substitute for the authenticated exact approval required in managed production.
- Older data may lack snapshot or complete historical binding proof. The code labels unavailable origins and refuses feedback where exact production consumption cannot be proved.
- The reviewed tests and code do not establish that deployed migrations, current remote branch integration or a live end-to-end customer run exist. A Jira Done state for earlier slices is not deployment evidence.
