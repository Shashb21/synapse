## One source-backed gap through the test contracts

The following is one **synthetic integration-test trace**, using real Postgres and controlled module data in `tests/accuracy-assembly-approval-integration.test.ts`. `fixture()` inserts `source.txt` and the parse block “Shared source text supports the selected item.” `gap()` creates “Approved exact gap” with the verbatim quote “supports the selected item.” The IDs below are runtime-generated fixture identifiers, not stable customer IDs.

1. `publishAssembly()` publishes the gap and tactic versions from successful test extraction runs. It binds `gapVersion.id` and `tacticVersion.id` in a `coverage_decide` input and output, then passes those exact IDs as `selections`, mapping endpoints and coverage run to `createAssembly()`. `createAssembly()` resolves the versions and calculates `assembly.checks` with `checkAssembly()` and `assembly.fingerprint` with `assemblyFingerprint()` from the selected content and lineage. The named test does **not** assert `assembly.checks.status` directly. Its later successful `approve()` call proves the review policy saw `checks.status === "passed"` with no blocking findings or unacknowledged advisories; those are required by `evaluateAssemblyReviewRequest()`. The separate `tests/accuracy-assembly-store.test.ts` test **“creates, reads, and retries an immutable mixed-origin assembly with server-resolved coverage”** directly asserts `assembly.checks.status === "passed"`, but uses a different fixture.
2. The fixture reviewer is `subject: "reviewer-subject"`, `provider: "test-idp"`, `role: "medical_affairs"`, with actor “Review Lead.” `approve(scope, assembly)` calls `reviewAssembly()` with `assembly_id: assembly.id`, `expected_fingerprint: assembly.fingerprint`, `expected_review_id: null`, `decision: "approve"`, rationale “Approved for exact live consumption.” and no advisory overrides. `reviewAssembly()` recomputes the check report and fingerprint, rejects stale production heads, applies the authorized-role/check policy, and stores the recomputed assembly and check fingerprints with reviewer identity. The named test does **not** inspect the returned review row or assert its generated review ID. The separate `tests/accuracy-assembly-review-store.test.ts` test **“stores exact approved review decisions and returns an identical initial retry”** asserts an approved review state and matching saved decision ID on another fixture.
3. The named test first asserts `approval_required` for managed reads and `merge_dedupe`. After `approve()`, it deliberately mutates the canonical claim row to “Mutable edit must not become live,” yet `listDownstreamClaims()` returns “Approved exact gap,” and `listCoveragePairs()` returns its “Approved exact tactic” pair with `partial` coverage. It then asserts `runAccuracyModule()` succeeds with two `merge_dedupe` survivors. That is direct evidence that this test's managed downstream projection used approved selected content rather than the mutable claim text. The test does **not** inspect the persisted consumer run's `assembly:approved-live-bindings` step. `kernel/run.ts` records and revalidates that step; the separate `tests/accuracy-assembly-feedback-store.test.ts` test **“records exact consumed items and immutable evidence for whole and subset feedback”** verifies historical review/assembly/item-version consumption proof using its own synthetic successful run.

These tests do not form one observed run from generated V0 through feedback. They establish linked implementation contracts through run IDs, item-version IDs, assembly fingerprint, check fingerprint, review ID and consumer bindings. No live customer extraction or paid provider response is represented. ## Deviations and rulings

- The original KAN-30 V1-versus-V3 example was illustrative. `runShallowAgenticCycle` records versions but its judge event says “Current latest-version policy”; it cannot itself choose an earlier supported V1. That remains an implementation/design gap.
- Deterministic source quote and assembly checks are useful safety gates, not semantic or clinical correctness. An approved assembly is eligible for managed downstream use, not proven complete or accurate.
- Production signals and KAN-42 contributor feedback are not gold outcomes. Only the isolated curated evaluator provides the supported source-item exact metrics. KAN-40's downstream dimensions are explicitly unscored.
- KAN-40's no-edit automatic gate in private benchmark copies is an experiment policy. It is not a substitute for the authenticated exact approval required in managed production.
- Older data may lack snapshot or complete historical binding proof. The code labels unavailable origins and refuses feedback where exact production consumption cannot be proved.
- The reviewed tests and code do not establish that deployed migrations, current remote branch integration or a live end-to-end customer run exist. A Jira Done state for earlier slices is not deployment evidence.
